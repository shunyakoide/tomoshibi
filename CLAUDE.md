# CLAUDE.md

灯 Tomoshibi (トモシビ) — a web app that generates **3D-printable forming molds (harigata)** for building washi paper lanterns (paper lamps). Editing the cross-section directly produces STLs for the ribs, koma (hubs), and stand.

## Terminology and roles (read this first)

The real-world lantern-making process: **wind bamboo ribs onto the mold → paste on washi paper → once dry, disassemble the mold and pull it out**. This app is about 3D-printing that mold as separable parts.

> **Grooves are horizontal rings by default** (identical position across every rib). An optional **spiral winding** mode (`p.spiral`) offsets the grooves per rib (`step/boards` each) so the bamboo forms one continuous descending helix; because each rib is then a different shape, spiral molds export one STL per rib, each engraved with its serial number (7-segment through-cut). Each part's role is as follows (**these definitions and relationships are fixed — do not change them arbitrarily in the implementation or explanations**).

```
        ● koma (top)         ← gear-like hub that gathers and bundles the rib tabs
      ┌──┐  neck (top)       ← vertical rectangle whose only job is positioning the opening (optional)
      │  │
     ╱    ╲                  lamp body (hibukuro) = the lantern's body shape.
    │ groove→ │ ← bamboo rib  Surface of revolution the washi is pasted onto. Bamboo-rib grooves on the outer edge.
    │ groove→ │
     ╲    ╱
      │  │  neck (bottom)     ← top and bottom are independent (neckBot / neckTop)
      └──┘
        ● koma (bottom)
       ╱ ╲                   ↑ tab (tsume) = the straight tongue at the rib's end. Plugs into the koma.
      stand (2 posts + base)  Receives the koma in a U-shaped saddle, holding it clear of the floor.
```

| Term | Role / definition |
|---|---|
| **lamp body (hibukuro / 火袋)** | The lantern's **body shape**. The curved surface the washi is pasted onto. The curved portion **between** the outermost control points of the cross-section profile. Bamboo-rib grooves go here and only here. |
| **rib (haneita / 羽根板)** | The **radial plate** that forms the mold's surface (N of them, arranged like the segments of a mandarin orange). A flat plate printed lying flat. Its outer edge is the lamp-body curve (+ grooves), with a tab at each end. It assembles by plugging into the two koma (top and bottom). Its inner edge is a curve **hollowed inward only at the center** (`ribInnerX()`) — to make it easy to pull out through the opening after drying (the same intent as carving the inside of a real forming mold into a half-moon). Note: "rib" (haneita) is a coined term for this app. Real craftspeople don't name the individual parts; they count by plate count — "**6-plate, 8-plate, 10-plate mold**". |
| **bamboo rib (higo / 竹ひご)** | The thin bamboo **wound horizontally** around the outside of the lamp body. The lantern's horizontal rings. It seats along the grooves on the rib's outer edge. Also called "**higo / bamboo bone**" in the real craft. |
| **groove (mizo / bamboo-rib groove)** | The **V-notch** carved into the rib's outer edge. So the bamboo rib seats in and doesn't slip off, the barb (tooth tip) leans toward **the center = the equator**. **Evenly spaced.** None are cut at the neck (near the opening). In craftspeople's terminology this side groove on the forming mold is called "**higo-me (ひご目)**" (the finer the count, the finer the work). |
| **opening (kaikou / 開口)** | The **mouth** at the top and bottom of the lamp body. = the radius of the outermost control point. It is the edge of the washi and the position where the koma/tabs connect. In real work this rim corresponds to the "**opening ring (kuchiwa / 口輪)**". |
| **neck (kubi / neck)** | The **vertical rectangular collar** standing outside the opening. Its role is **"only" to set the position and size of the opening**. It is independent top/bottom and can be present or absent (`neckBot`/`neckTop`). **Always a rectangle — never angled.** **The presence of a neck does not change the tab size.** Without a neck, the opening becomes the tab size. The neck carries no bamboo rib, no groove, and no washi. |
| **tab (tsume / tab)** | The **straight tongue** at the rib's end. It plugs into the koma's notch. Width = **board thickness `boardT`** (nominally equal to the koma's notch width). Only the notch side adds the **print tolerance `fit`** to become `boardT + fit`, leaving a real-world fit clearance (the tab itself stays `boardT`). No **outward** steps, hooks, or protrusions. **Both tabs** have an **L-notch dented into the tip's inner corner** (`TAB_DENT_W`×`TAB_DENT_H`), which the koma's shallower notch mates with: the wider tab base then catches the koma's solid hub and stops it sliding inward. In a lantern maker's mold there is no neck and "tab = neck" (which is why the neck is an optional design element). |
| **koma (コマ)** | The **small gear-like hub** that gathers and bundles the tabs (two of them, top and bottom, completely identical). Notches around the rim where the tabs plug in. Outer diameter = `komaR`. The stand receives it. This is a **real craft term**; in the trade it is also called "**kagami (mirror / 鏡)**" (the forming mold is assembled and fixed by inserting it into the grooves of the top and bottom koma = kagami). |
| **stand (dodai / 土台)** | The **base** that supports the assembled mold. Two **posts** of constant thickness receive the koma's rim in a U-shaped saddle, and a single base plate holds the posts at the correct spacing. Fully flat, needs no print supports. Users often reuse it (they don't print it every time). |
| **opening ring (kuchiwa / 口輪)** | **The one exported part that is not part of the mold** — it stays in the finished lantern, which has no koma left in it once the mold is pulled out. A thin flat hoop (`ringGeometry`, `RING_WALL`/`RING_H` = 2mm) glued around the opening to hold it round, sized from `openingR()` so it follows the design like every other part. The **bottom** one also carries the **leg sockets** (see below); the top one is a plain hoop. |
| **leg socket (脚ソケット)** | The **flat "onigiri" pads** inside the bottom opening ring — `LEG_N`=3 of them at 120°, each pointing its rounded vertex at the centre with a **bore** (`LEG_D`=6mm) at its middle that a leg rod pushes into. This is what makes the bottom ring double as the base of a **stand for the finished lantern**. Each pad's two outer corners stay sharp and overlap the hoop's inner rim by `LEG_OVERLAP`, so the whole thing prints as one piece; the pads are the same height as the hoop (flat, no supports). Presence is `p.legSockets` — **a checkbox, not dimensions** (see below). |

**Assembly relationships**: rib (tab) → plugs into → **koma** → sits on → **stand**. (The **opening ring** joins nothing here — it belongs to the finished lantern, after the mold is taken apart.) The bamboo rib winds into the **grooves** on the rib's outer edge. The rib's outer edge revolved forms the **lamp body** surface onto which the washi is pasted. The **neck** positions the opening (a vertical rectangle) and is **independent of the tab size**.

## Commands

```bash
npm run dev       # Vite dev server (HMR, --host). http://localhost:8173/ (strictPort: a clash fails loudly)
npm run build     # Production build (= npx vite build). Always confirm it passes after changes.
npm run preview   # Preview the build output
```

No test runner. **Correctness is verified by "the build passes" + "the STL is watertight (manifold)"** (see below).

## Tech stack

Vite 8 + React 19 + three.js r185 + fflate (all plain JS/JSX, no TypeScript). Minimal dependencies — four runtime deps, two dev.

## Architecture

- **`src/geometry.js`** — the core, and the **single import point for every shape**. **Pure functions** that generate the cross-section profile and the 2D cross-sections / 3D geometry of every part. They return three.js Shape/ExtrudeGeometry but **have no dependency on React or the DOM** (shared by section drawing, 3D preview, STL export and both paper templates — which is why what you see is what you print). The file itself is now a **re-export barrel**; the implementation sits in `src/geometry/`, one module per part:
  - **`geometry/profile.js`** — `outerR()` and **every dimension derived from it** (`komaR`, `tabDepth`, `innerRi`, `notchR`, `maxBoards`). These share a module because they are genuinely mutually recursive, not merely related: `outerR` calls `komaR` (a neck-less end *is* the tab size) and `komaR` calls `outerR` via `bodyMinR`'s self-intersection guard. **The print-fit invariants live here** (see "Part joints" below) — this is the file to be careful in.
  - **`geometry/groove.js`** — groove positions / width / the grooved outer edge · **`geometry/shape.js`** — point list → `THREE.Shape` with the cleanup earcut requires · **`geometry/rib.js`** · **`geometry/koma.js`** · **`geometry/ring.js`** (the opening rings + the bottom one's leg sockets) · **`geometry/stand.js`** · **`geometry/washi.js`**
  - **Import from `geometry.js`, not from the modules.** The barrel's public surface is deliberately the same 40 names it was before the split, so moving a function between modules stays a non-event for callers. Dependencies run one way (profile ← groove ← rib; shape is a leaf) — **anything mutually recursive with `outerR` belongs in `profile.js` by construction**, or you have created a cycle.
  - Add geometry logic to the module that owns the part. `check:hash` makes any move provably shape-neutral: the split itself was verified at zero vertex diff across all 1152 parts.
- **`src/config.js`** — `PRESETS` (control-point templates for shapes) / `DEFAULTS` (initial parameters) / `SIL_ROWS` (scrub-row definitions) / **`LIMITS`** (how far the body may be stretched — see "How big may a design get" below).
- **`src/SectionEditor.jsx`** — the **direct-manipulation editor** for the cross-section (SVG). Drag/add/delete control-point ◇ handles, toggle corner/smooth, and visualize the neck/lamp-body/tab (rib). It uses `geometry.js`'s `outerR` etc. directly so it matches the 3D/STL exactly.
- **`src/TomoshibiStudio.jsx`** — the app's **state and composition only**. It holds the design `p` and the transient UI state, wires the hooks, and lays out the viewport + inspector. It renders no control of its own and builds no 3D — those moved out (below). Keep it that way: the moment a scene detail or a button's styling lands back here, the file starts growing towards the 1,400 lines it used to be.
- **`src/three/viewport.js`** — everything created **once per mount**: renderer, post-processing chain, lights, shared materials, camera-orbit input, and the render loop. Input is a single **pointer-event** path (mouse / touch / pen, with pinch derived from the live pointers) and every listener is removed on dispose — the earlier mouse+touch pair left window listeners behind, so a StrictMode remount rotated the camera twice per drag.
- **`src/three/scenes.js`** — `buildScene()` and one builder per view (`mold` / `print` / `lit`). Two views draw no 3D at all and say so by returning early: `2d`, and `print` on the cardboard route — both are documents drawn over this canvas instead. It empties the viewport's group and refills it. Every shape comes from `geometry.js`; the only geometry it touches is rotating parts flat for the **print preview**, which is preview-only (the export lays parts out itself).
- **`src/bed.js`** — `fitOnBed()`. Shared by the overflow warning, the recommended max height, and the plate layout, so those three can never disagree.
- **`src/hooks.js`** — `useUndoRedo` (watches `p` and commits once it settles, since there is no single choke point for edits) / `useAutosave` / `useNarrow` (`useSyncExternalStore`, so the first render already knows) / `useLang`.
- **`src/ui/`** — `theme.js` (the palette + the `t` context — see below), `controls.jsx` (ScrubRow / Stepper / NumInput / Checkbox / SegButton / CTA / Note — ScrubRow takes an optional `curve` for rows whose range far outruns the sizes people work at), and the panel's larger pieces: `PresetChips.jsx`, `PointCard.jsx`, `Toolbar.jsx`.
- **`src/GuidePage.jsx`** — the **assembly guide** (the 作り方 view): how to build the lantern. It is a document, so it takes the whole window (no inspector, like the lit view) and overlays the idle canvas the way the section editor does. **The page is generic: every figure is drawn from one fixed design (`GUIDE_P` = `DEFAULTS`, plus a `paperP` copy for the cardboard route), and no dimension is printed anywhere on it.** It used to be the opposite — the parts measured off `geometry.js` and every figure rebuilt when a slider moved — and that was dropped at the user's request: two dozen WebGL scenes on every edit, bought with numbers nobody needs, because winding bamboo onto a mold and pasting paper over it is the same job at ⌀140 as at ⌀400. Figures are therefore built at most **once per route per session** (`CACHE` in GuidePage) and a return visit costs no WebGL at all. **What this gives up is the old guarantee that the page could not describe a mold the download does not contain, so nothing on it may state a QUANTITY the design decides**: the rib's line reads 「設計した枚数」 rather than ×8 for exactly that reason (a fixed picture of eight ribs is an illustration; a printed 8 is a claim), while ×2 koma, ×2 posts, ×1 base and ×1 ring each stay, being facts about the mold. The one thing that still follows the app is the **route**, because that changes which parts exist at all, not how big they are. Between that list and the steps sits **`KIT`** — what you supply yourself (bamboo, washi, paste, tape-or-thread, a razor, a lamp, wire; two brushes and pliers). **Plain strings, no numbers, nothing derived**: a wire gauge and a brush are not things the design decides, and a bamboo length summed over the grooves was tried and taken straight back out — arithmetic nobody asked for on a list whose job is to be read in a shop. Its items carry `opt` (a 「任意」 badge on the name line, where the parts list puts its ×N — the same line answering the same question) and each one draws, in the parts grid's own card and well, from a `fig` in figures.js (see the kit note there). What is optional is a judgement, not a category: the wire and the pliers serve only the two lighting ways that fix something to an opening (way (1) stands a lamp on the floor and needs neither) and the brushes are a preference, so **everything else is unconditional** — without bamboo, washi, paste, something to hold the bamboo while it dries, a blade to trim the paper and a lamp to put inside, there is no lantern at the end. The **razor sits among the materials rather than the tools** because that is where it was asked for; it is also the one cutting thing on the page you use up. Tape and thread are **one card and one drawing** (`kitStick`), and the card is named for the job rather than for either of them (「テープや糸など」): anything that holds the bamboo while the paste dries will do, a card each would be the list saying the same thing twice, and a note hung under one of them ("or superglue") reads as an alternative to that one rather than to both. **Every step is drawn** — winding the bamboo, pasting the washi, drying, pulling the mold, and the lantern lit. Steps that were pure technique used to take a **photograph** from `public/photos/`, with a slot naming the file it was waiting for; nothing is waiting on one any more, so that mechanism was removed rather than left behind unused (bring it back with the step that needs it). Why the drawn ones are drawn: the rings come from the same `grooveList`/`higoSpiralPath` that cut the grooves (so a spiral mold is drawn as one continuous helix), and the panels are one lathe per bay over `fukuroRange` at `outerR + higoD` — the lit view's own skin radius — so the seams fall on the ribs of the mold being drawn. Neither is something a photograph of somebody else's lantern can say, and both are why these stayed drawings when they stopped being derived. The washi figure is the mold **in its stand** (upright on cardboard, which has no stand) with panels on **every other bay** — the order the step asks for — and two fixed points behind it: **pasted panels are ivory**, breaking the white-parts rule, because paper laid over a white part on a white card is invisible; and the **mold is yawed so a bay centre faces the camera**, which is the only way two alternating panels are both fully front-facing (a bay is 360/N wide, so any other phase lays one across the silhouette, where its inside shows through the bare bay with the bamboo drawn over it). A mold has no preferred rotation, so the yaw costs nothing. The **paper's surface is the mold's offset along its NORMAL**, not along x (`washiProfile`): a horizontal offset leaves only `higoD·cos θ` of clearance on a face at angle θ, and past ~60° the bamboo comes out through the paper it is under — a squat body (r=120 on h=90 is dR/dy = 2) drew its bamboo as rings printed on the outside of the shade. The **pull** figure is the same dry shade **lying on its side**, both koma set down flat and the **last** rib half drawn out of the opening (one rib, not eight: they come out one at a time, and with the rest still in, the mouth fills with rib edges seen end-on and reads as a turbine): the rib leaves along the axis, so upright the whole action points at the camera. It is the rib that faces the camera (`faceOnRib`), brought onto the axis on its way out — which is what the hollowed inner edge is for — and it leaves by the **wider of the two openings**: a rib is as wide as the body is deep, and the default lantern's mouths are ⌀148 and ⌀38, so out of the small one it does not read as the wrong end, it reads as the rib tearing through the paper. The bands are gone, because with the koma off there is nothing for them to hold; the mold is yawed 15° off square (`PULL_YAW`) because at 0° the mouth faces the reader and the frame fills with the inside of the lantern, and at 45° it is edge-on and the shade flattens into a leaf. The **light** step is the finished lantern with no mold in it at all — warm rather than white, because a lit shade is the same paper with light behind it, and no rays (a starburst is the one mark on a page of technical drawings that would be decoration). It is the one step with **`options`**: three ways of supplying the lamp, each its own **section** with its own figure. **Sections, not steps** — numbering them 11/12/13 would tell the reader to do all three — and each needs its own drawing, because the difference between the three *is* the picture. Each way's **title and body sit above its figure**, spanning both columns — that is what separates one from the next. Beside the figure the title is only the first line of a paragraph in a column of paragraphs. It also leaves the right-hand column holding nothing but the numbered work, so **that column's first well starts level with the main drawing** rather than a paragraph's depth below it. (Giving each way its own card was tried and taken back out: it separated them, but by more than they needed.) (1) `lightSet`, a lamp stood on the floor and the shade dropped over it, drawn **exploded**: set down it is indistinguishable from the other two with their fittings cropped off, and lifted it states the whole method. The floor disc is what separates "stood on the floor" from "floating", and the lamp is generic (a base and a dome, no thread) sized off the **bottom opening it has to pass through**. (2) `lightHang`, hung from a pendant cord: the cord is on the **axis** and enters by the **top** opening whichever is wider — a hanging shade has an up, and it is the design's own up, not its bigger mouth — and its top is simply **cut off**, the convention for "this continues"; a ceiling rose would claim the lamp is wired in when it plugs into a socket. (3) `lightLegs`, stood on legs with the lamp fixed up into the bottom mouth: the legs are the lit view's (`scenes.js` buildLit: 0.42·height drop, 0.35·drop splay) rooted in the bottom ring's **sockets** (`ringLegs` gives the pad centres). Its cord **turns and runs out of the frame** — straight down between three legs it read as a fourth leg — and **no socket is drawn**, because the view looks down on the lantern so anything in the bottom mouth is behind the paper, and one dropped far enough to clear the rim would be inventing the fitting this step has not designed. **An option can carry `detail`** — the numbered work inside it, numbered *because* it is sequential, which is exactly what the options around it are not. A slot is filled in by gaining `title`/`body`/`fig`; without a `fig` it keeps an empty well and 「未記入」, which says the step is unfinished where three tidy sentences would say it was finished and thin. **(3)'s three are filled and (2)'s two are not**, and that is the state of the design rather than of the writing: the legs are held by a method that needs nothing printed — a pendant holder's cord leaves through a threaded stem with a fixing nut on it, so a loop bent in the end of each leg wire stacks on that stem and one nut clamps all three (`legBend`/`legStack`/`legStood` in figures.js) — while what grips the paper when the lantern HANGS is still open. The three read the same on both routes on purpose: they stop at the bench, and what the legs are then pushed into is the opening's ring, which the option's own `body`/`paperBody` already names per route (a slot has no `paperBody` of its own, and should not need one). **An option can be dropped: `needs(p, stl)`.** (3) requires the leg sockets, so it disappears when they are off and when the opening is too small for them — drawing a legless lantern under the words "add legs" is the same lie as printing a rib count the reader's design does not have. Now that `p` is the FIXED design it always passes, and it stays for two reasons: it is what would drop the way if `GUIDE_P` ever lost its sockets, and the lead says **`{n}` ways** counting what is actually offered rather than restating three. It does **not** require the 3D route, though. Cardboard prints no ring, but the finished lantern has an opening ring either way — only who supplies it changes — so that route gets the same option and the same figure, with a **`paperBody`** saying the hoop is yours to make from card. `ringLegs` is a question about the opening, not about a printed part, which is why it answers on both routes. A step can be marked **`wip`** — a `draft` badge beside its title and the field's own one-line reason under the body. The **light** step is one, and the reason **names the one way still open** (「吊るす場合の…」): it used to say the lamp fitting in general, which stopped being true the day (3) got a fixing worked out in full — a draft label hanging over three drawn sub-steps says the wrong thing about them. (1) fixes nothing to anything, so hanging is what is left. The note says **opening, not ring** — the cardboard route prints no rings, and a step must not name a part its own route never makes. It used to offer a ⌀65 lamp-holder base to print (`tomoshibi_socket_base.stl`, which was never in `public/` — the link 404'd); that fitting is exactly what is being reconsidered, so the download went with the badge. Don't put a download back on a step whose part is undecided: a file someone prints is a decision, and the badge cannot un-print it. It is a field on the step, not a hard-coded sentence, so the next unsettled step brings its own reason. Print styles in `index.css` make the browser's own "Save as PDF" the paper version — **the app writes no PDF for this page**, which is the whole reason it is a page. Two things there are load-bearing and were both found broken. **The shell has to be released first**: the app is a 100%-tall, `overflow: hidden` box from `<html>` down to the viewport — correct for a tool that fills the window, and it clipped the printed guide to **exactly one page**. Styling `.guide` alone never reached it. And **the two-column layout has to be forced back on paper**: sheet width is under the 860px breakpoint, so the page fell to one column and every figure grew to full width — a page per step, and option blocks taller than a sheet, which Chrome dropped rather than split (11 steps came out as 8 pages ending at step 8). With both fixed the page prints complete (6 sheets as it stands; it was 5 before the kit list grew, and the number is content, not a rule). If you change either rule, print it and count the pages — nothing else here looks at paper.
- **`src/three/figures.js`** — those figures: white faces (`MeshBasicMaterial`) plus `EdgesGeometry` outlines, orthographic and isometric, rendered **off-screen to a PNG data URL** by one reused renderer. Eleven live canvases would be eleven WebGL contexts; an `<img>` costs nothing to scroll and is what the print path can paginate. Two things here are not obvious: a **surface of revolution has no creases**, so the pasted shade is built as **one lathe per bay** rather than one skin — a full lathe gives `EdgesGeometry` nothing but its two rims and prints as a blob with no outline, while per bay the seams draw and the outermost ones land on the silhouette (they are also what a real shade shows); and the frustum is fitted to the **projected** bounding box, because sizing by the largest dimension leaves a rib a fifth of its frame. The **kit** scenes (`kit*`) are the only ones left that were never built from `p` (the rest are now drawn from a fixed design too — see GuidePage): a pot of paste, a roll of tape and a shoe brush are constants, and their numbers are **proportions rather than dimensions** (a real 糊刷毛 is ~130mm wide with 30mm of bristle; the frame is fitted per figure, so only the ratios survive). They are drawn **white, exactly like a part** — `solid()` is `part()` under another name — rather than given a fill of their own, so a kit item and a mold part read as the same kind of drawing rather than two different ones. That was tried with a fill first and reverted: a round shape (a tub, a reel, a coil) draws no side lines at all — a 24-sided cylinder none, a 12-sided one a hatch — so white-on-white made the bamboo and wire coils nearly vanish, and the fix is the one this file already leans on everywhere else, not a colour: `coil()` drops to **8 radial segments**, whose 45° facets clear the 24° edge threshold and draw as a faceted rod. A **brush** needs one thing a flat white solid still can't say for itself — that the block under the handle is bristle, not more handle — so `bristleFringe()` hangs a few short lines off its front-bottom edge. Not a texture: the same INK, the same kind of line the rest of the page draws its facts with. Every such stroke — bristle, silhouette, knurl, the razor's bevels — is built by the one `inkLines()` helper, and **`silhouetteCircle()` is `silhouetteLines()` for a sphere** (a ball's outline is a circle of its own radius in the plane facing the camera), which is what lets the lamp be drawn as a smooth bulb rather than a faceted one. The **razor** is the 長柄カミソリ, not a loose double-edge blade: that one was drawn first and is the more iconic object, but nobody trims a wet edge holding a bare blade in their fingers. Its whole shape is the outline — a slim stick, a shoulder where the head widens out of the grip, a slanted tail — with the guard rail on top and the comb teeth drawn across it, teeth being the only thing that says which end cuts. The **washi** is four thin sheets fanned a few degrees each: square they are one white block, turned they are loose paper, and the TOP sheet is the un-turned one because it is the only one drawn whole (everything it does not cover has to read as a corner). The **lamp** card draws TWO (`lamps()`): a bulb hanging in its pendant holder, and a flat USB puck — laid out by `tapeAndThread`'s rule (side by side across the view, clear in plan so only the drawing overlaps). Two, because the three lighting ways want different fittings, so the card says what the light has to BE rather than picking one. **The holder is not a card of its own**: alone it is a fitting, and this list answers "what do I need in front of me", so it is drawn with a bulb screwed into it and the pair is simply a lamp. Its cord is CORD_INK and cut off at the top, `lightHang`'s convention, and short — the frame is fitted to what is in it, so cord is drawn at the socket's expense. The puck is turned so its lead runs away from the glass (pointing at it, the plug read as something stuck on), and its aspect is a real one (KAPPLAKE is ⌀35×10, so 3.5:1) while its SIZE is not: at true scale beside a bulb it is a dot in a 300px well. Hanging the bulb needs **`DIR_UPSIDE_DOWN`** — `ledBulb` takes the view direction in its own frame, because every line on it is a silhouette and a silhouette is a fact about where the camera is; flipped without it, the globe's outline circle draws as an ellipse across the glass. The **fitting** figures at the foot of the file (`legBend`/`legStack`/`legStood`) are the light step's way (3) in three, and they ignore `p` for the kit's reason — a socket, a nut and a metre of wire are things you buy. They draw the holder the way that step leaves it: **mouth up, stem and cord down**, which is the whole difference between (3) and (2) upside down, and they take the shell's two dimensions from the same constants the kit's own socket does rather than redrawing it by eye. Three things there were found the hard way. The loops sit **well down the stem**: the shell is ⌀34 over a ⌀11 stem and the view looks down, so loops up against its underside are *under* it — all three vanished and left three arms coming out of nothing. The wire is a **solid accent rod with INK outlines**, not the plain filled tube the option's own figure gives its legs: filled, three stacked loops merge into one orange blob, and the outline over 8 facets (`coil()`'s trick) is what separates the turns. And the triad is **deliberately not phased** — one leg always lies along the view axis, and a leg pointing AWAY is odd-looking but countable, where a leg pointing AT the reader collapses to a stub behind the socket and the figure shows two. The cord leaves through a **gap between legs**, for the reason `lightLegs` turns its own: a dark line among three legs is read as a fourth. There is **no arrow on the nut**, though the reference drawing for this has one: nothing else on the page has an arrow, and the nut drawn off the thread in one figure and run up tight in the next is the exploded-then-assembled pair `lightSet` already uses.
- **`src/PagePreview.jsx`** — the **cardboard route's print view**: the template's pages rendered from `paperPagesSVG()` and laid out like a PDF viewer's. Presentational; it owns no state and computes no dimension (see "Build route" below). It used to export a second component, `WashiPreview`, docking the washi sheets in the print view's left gutter; **that is gone and should not come back** — see "Washi template".
- **`src/Welcome.jsx`** — the **first-run onboarding card**, which also asks the one setup question (3D printer or cardboard — see "Build route" below). Presentational only: no app state, no geometry.
- **`src/pdf.js`** — minimal, dependency-free **PDF writer** (vector only). Consumes the same drawing ops as the SVG renderer, so the printed PDF and the printed HTML are the same drawing. Used for both templates bundled in the route's ZIP. Latin is base-14 Helvetica; **everything WinAnsi cannot encode is drawn as filled outlines** from **`src/pdf-glyphs.js`**, which `tools/pdffont/build.py` extracts from an OFL font for exactly the characters the templates print (24 of them, 12 kB — a whole CJK font would dwarf the file). That is what ended the templates' English-only era: hand them the Japanese translator and the words print instead of being dropped. The glyph table is **generated — never hand-edited** (rerun the tool), and `npm run check:glyphs` reruns the tool's own collection to fail on both a character with no outline and an outline nothing prints. Two rules follow from the encoding: a glyph is *text*, so anything reading the content stream must strip glyph blocks before counting paths (`check:paper` does), and the **matrix that scales a glyph needs more than 3dp** — `size/1000` is 0.0034 for a 3.4mm label, and rounding that to 0.003 draws every character 12% oversized and laps it over its neighbour.
- **`src/stl.js`** — STL / ZIP export (+ `downloadFile`, the one place a Blob becomes a download). Both formats are written by libraries rather than by hand: three's **`STLExporter`** (its face-normal maths is identical to the writer this file used to carry — verified byte-for-byte across four designs) and **`fflate`**'s `zipSync`. The old ZIP could only STORE; DEFLATE takes a default kit from ~1.0 MB to ~0.19 MB. `zipSync` tree-shakes to 9.5 kB raw / 4.8 kB gzip, the only reason a dependency was worth it here — contrast `pdf.js`, where the equivalent library costs hundreds of kB for a handful of vector ops.
- **`src/papercraft.js`** — **papercraft** (A4 full-scale 1:1 print pages for building the mold from cardboard/thick paper) and the **washi template** (`washiParts` / `washiPDF`, the paper skin's own flat pattern). A pure module that derives the drawing from `geometry.js`'s 2D functions (see "Papercraft" / "Washi template" below). Everything goes through one page pipeline — `pageOps()` (clip band, trim box, check square, coded half-diamonds) rendered as PDF by `pagesPDF()` for both deliverables, or as SVG by `paperPagesSVG()` for the in-app preview — so the print rules can't drift apart between templates or between the two encodings.
- `main.jsx` — entry point (+ the error boundary that keeps a render error from blacking out the screen).
- **`src/index.css`** — reset, range-slider skin, focus ring, and the inspector's **component classes** (`.btn`, `.seg`, `.cta`, `.chip`, `.scrub-row`, …). Two rules for working here: the **palette is defined in `ui/theme.js`**, which publishes it as custom properties at startup (it has to live in JS because SVG presentation attributes need a real colour, not a `var()`); and anything that depends on **state a style attribute cannot express** — `:hover`, `:disabled`, `[aria-pressed="true"]` — belongs here rather than as a ternary in JSX.

## Coordinate system and units

- **All dimensions in mm.** Ribs/koma/stand are a **Shape on the XY plane + extruded along Z** (= oriented for flat printing as-is).
- `outerR(p, t)`: height-normalized `t∈[0,1]` (0 = bottom, 1 = top) → outer radius in mm. The heart of the profile.

## Profile model (important)

The silhouette is a radius function connecting the **control-point array `p.pts = [{t, r, sharp?}]`** (ascending) via **monotone Hermite interpolation** (Fritsch–Carlson, `fukuroTangents`/`fukuroSpline`). To suppress warping and unwanted sharp curves, tangents are clamped to the same sign as the adjacent chords and to within 3×.

- **The outermost control points (`pts[0]` / last) = the opening = the neck radius.** Matching them here removes any wasteful flare (S-curve) from the neck into the lamp body.
- **The neck (kubi)** = a **vertical rectangle** outside the outermost control point (always a rectangle — never angled). Presence is independent top/bottom via `neckBot` / `neckTop`. The neck's height and overhang are adjusted with the ◇ handle in the section view (horizontal = overhang / vertical = neck height).
- **The lamp body (hibukuro)** = the curve **between** the outermost control points + bamboo-rib grooves. `fukuroRange(p)` gives its t range.
- **The design reference for the neck and tab is "the control-point radius"** (`openMin`/`bodyMinR`), and it **does not depend on whether the neck exists**. Toggling the neck does not change the tab (koma) size. On the side without a neck, the opening becomes the tab size (`komaR`).

## How big may a design get (`LIMITS`)

`src/config.js` holds one table — `LIMITS = { height: [60, 2000], r: [10, 600] }`, in mm — and **everything that clamps a silhouette value reads it**: the section editor's ◇ drag and its `+` ghost, the typed radius field, the height scrub row, and `persist.js`'s sanitize. Four separate copies is how you get a design that snaps back the moment you touch it somewhere else; the old code had exactly that (the editor clamped radius to 130, persist to 140, and persist's floor was 8 where the editor's was 10).

- **The floors are geometry. The ceilings are not.** `r = 10` is the wall: below it the opening is narrower than the rib's own core (`innerRi`), so the tab is wider than the mouth it has to come out of. Every height from 30 to 2000mm fails at r=8 and passes at r=10 — it is not a preference, and `check:manifold`'s cylinder family exists to keep it honest. The ceilings only stop a corrupt file or a fat-fingered typed value from asking for a metre-per-mm lantern; `check:manifold` sweeps the whole box watertight, and a festival 大提灯 is about ⌀1m, so ⌀1.2m is headroom, not a design decision.
- **These used to be 140–400mm and 10–130mm, and the wall was reachable by hand** — dragging a ◇ simply stopped. Widening them is what surfaced the slope-dependent lightening-window bug (see "STL watertightness" below), which was already reachable inside the *old* caps (a barrel scaled to r=130 at h=140 reaches dR/dy = 4.4) and invisible because nothing in any sweep scaled the control points.
- **The section view fits both axes**: `s = min(2.0, 520/H, (CX-30)/maxRadius(p))`. The first two terms are unchanged, so nothing that fitted before is redrawn at a different size; the width term only ever makes it smaller. Without it a wide, low body runs off the sides of the frame, taking the ◇ you are dragging with it. The 3D views needed nothing — `frame()` already sizes itself from `maxRadius(p)` and `p.height`, far plane included.
- **The height scrub row is non-linear** (`curve: 2.5` — see ScrubRow). Over 60–2000mm a linear slider spends 93% of itself above the sizes anyone builds; the curve gives 60–400mm half the bar, and one arrow-key step is still ~1mm at 205mm. Don't widen a range past a few multiples without it.
- **A bed-overflow hint of "→ reduce the body height" is only true when some height fits.** `heightLimit` returns 0 when none does — a ⌀1.1m rib overflows a 256mm bed at *any* height, and the parts are too wide, not too tall.

## Design rules (repeatedly raised points — fixed items so they don't need re-explaining)

Always obey the following when changing the shape. Removing these has caused reverts in the past:

- **The neck is always a vertical rectangle.** No slanted taper or angle. Its only role is positioning the opening.
- **Do not change the tab (koma) size based on whether a neck exists.** The neck widens the opening outward. Without a neck, opening = tab size.
- **The tab is a straight tongue.** No **outward** steps, hooks, or protrusions (the outer edge matches the koma outer diameter `kR` exactly and does not stick out).
- **Exception: the koma stop = the tab-tip dent** (added by reference to a real paper-lamp mold). **Both tabs** get an **L-notch cut out of the tip's inner (small-radius) corner** — `TAB_DENT_W`=6mm radially × `TAB_DENT_H`=6mm along the tab. The tip's inner edge pulls in to `innerRi + TAB_DENT_W` while the tab **base** stays at `innerRi`, and the koma's notch bottom is set to that same dented radius (`tabTipRi` → `notchR`), so **the wider tab base catches the koma's solid hub** and the koma cannot slide inward toward the lamp body.
  - **The koma is pulled out "outward" (toward the tab tip) after work.** The catch is a single inward step, not a clamp from both sides → nothing to ride over, so insertion/removal stays free. Blocking this makes the mold impossible to disassemble.
  - **The catch cannot drift between the two parts**: `ribOutline2D()` (which cuts the dent) and `komaShape()` (which cuts the notch) both derive from `tabTipRi()`. Change one and you change both.
  - `tabDented(p)` decides whether there is room (needs `tabLen > TAB_DENT_H+1` and `komaR - innerRi > TAB_DENT_W+2`); with no room it falls back to a plain straight tongue + full-depth notch. **`p.noTabDent` forces that fallback** — the cardboard papercraft sets it (see below).
  - Nothing here moves the stand: the dent only reshapes the tab tip, and `komaR()`/`standSlotSep()` do not depend on it.
  - **History**: this replaced an earlier "inward shelf on the top tab only" (`komaStop2D()`), which was removed. Don't reintroduce a shelf.
- **Tab width = board thickness `boardT`** (nominally equal to notch width). Notch width = `boardT + fit` (`fit` = print tolerance, added in `komaShape()`). Rather than "cramming it tight", match nominally and leave only the real-world clearance `fit`. With `fit=0` there is no gap, as before.
- **Hollow the rib's inner edge "only at the center"** (`ribInnerX()`). Real paper-lamp molds have this shape, to make the rib easy to pull out through the opening. **Do not bend the whole rib** (bending it end-to-end makes an impossible shape / a constant-width band gives an opening ≫ koma shape that never reaches the tab, splitting the rib in two). The top and bottom ends stay at **core `Ri`**, so the connection to the tab is unchanged. The hollow amount is the center depth × `RIB_CURVE_D` (real ones are about 20%). **It does not propagate to the outer edge, grooves, tab, koma, or stand** (only the inner material is reduced).
- **The groove's barb (tooth tip) leans toward the center = the equator** (not toward the opening). Do not place grooves right next to the opening; leave a half-pitch buffer (barbs at the very end don't work).
- **Grooves go evenly spaced across the entire lamp-body curve.** The curve always needs grooves.
- **Curves stay smooth.** Do not create wasteful sharp curves or S-warps derived from the control points (matching the outermost control point = the opening removes the flare at the neck).
- **Don't casually change the height or the stand.** Users reuse the stand. Dimension changes propagate to the joints (below).

## Leg sockets on the bottom opening ring

The bottom ring doubles as the base of a stand for the **finished lantern**. Fixed items:

- **This was removed once (`f8447e2`, 2026-08-19) and put back deliberately.** That commit dropped the pads on the grounds that "the stand they were for is still undesigned", and left the ring a plain hoop with a marker tab. Do not remove them again on that reasoning: an undesigned stand is a reason to leave the sockets alone, not to delete the only feature that lets one exist.
- **The dimensions are CONSTANTS and stay constants (`LEG_N` / `LEG_D` / `TRI_R`).** The design says only **whether it wants sockets** — `p.legSockets`, one checkbox. They were never settings, and a leg count and rod diameter are not two more things to tune: a lantern either stands on legs or it doesn't, and a rod gets trimmed to the hole rather than the hole opened to the rod. Numeric controls for these were tried once and taken straight back out; don't re-add them.
- **`ringLegs(p)` is the single answer to "are there sockets".** `ringGeometry` and the inspector both call it, so the panel cannot claim sockets the part does not have. It returns `null` when the flag is off, and on the two ways the pads run out of room — the inward vertex crossing the ring's axis (`PAD_CORE`), and neighbours touching (`PAD_GAP`) — and the ring then falls back to a plain hoop. The small-opening case is reachable inside `LIMITS`: at the ⌀20 floor the pads fold through each other.
- **`ringLegsFit(p)` asks the second question without the first.** "You turned them off" and "they will not fit here" are different sentences and only one of them is news, so the hint appears only when the design asked for sockets and the opening refused.
- **The marker tab is cut exactly when the sockets are not.** Its whole reason is that the two rings would otherwise be the same hoop in two sizes (the sphere preset's openings are ⌀60 vs ⌀56). With sockets there is nothing to confuse, and the tab reaches 1.35mm past the nominal opening — a cost with no benefit. One `if`, not two independent decisions.
- **Verification is `check:manifold`'s leg-socket section, and the bore test in it is not optional.** The pads are separate closed shells merged into the hoop, so **edge counting is blind to a bore that got filled in** — the shell stays closed and a ring you cannot put a leg in passes. So it shoots a ray up each pad's middle and counts the faces over it (0 = open, 2 = capped), plus the two geometric conditions `ringLegs` exists to enforce and the fact that the flag being off really does cut nothing.

## Part joints (invariants for printing and assembling)

The mold is **rib × N + koma × 2 + stand**. Whether a reprint "fits the previous koma/stand" is determined by these values:

- **Rib tab ↔ koma**: board thickness `boardT` (the tab's thickness; notch width is `boardT + fit`) / `innerRi` (tab tip = notch-bottom radius) / `boards` (tooth count). If these three are the same, the tab plugs in to the same depth. `fit` only adds tangential fit clearance and does not affect engagement depth. `komaR` (koma outer diameter) only sets the koma's outward overhang and does not affect engagement.
  - **Implementation**: this engagement is **consolidated into the single function `innerRi()`** (`src/geometry/profile.js`). Because `ribOutline2D()` (which makes the tab) and `komaShape()` (which cuts the notch) **call the same `innerRi()`**, the tab-tip depth and the notch bottom necessarily match. The only place that can break this invariant is `innerRi()` alone. Check the impact on both before touching it.
  - **Tab depth (engagement) and stand independence**: `innerRi()` is the legacy reference `nominalRi()` deepened toward the center by `TAB_DEEPEN` (tab tip / notch bottom). Meanwhile `komaR()` is based on `nominalRi()`, so **deepening the tab does not move komaR = the stand dimensions**. To prevent the wall between adjacent tab notches from getting thin and non-manifold from over-deepening, `ribCoreFloor()` (computed from the minimum inter-tooth wall thickness MIN_WALL) imposes a center-side limit.
  - **Notch bottom `notchR()` is also shared**: `komaShape()` (which cuts the notch) and `ribOutline2D()` (which cuts the tab-tip dent) both trace back to `tabTipRi()` → `notchR()`. With a dent the notch is **shallower** (its bottom sits at the dent radius) and the tab base, further in at `innerRi`, is what catches the hub. The deeper `TAB_DEEPEN`, the less room `tabDented()` has to find (both fight over the same inner space).
- **Koma ↔ stand**: `komaR` (saddle receiving radius = `komaR + SADDLE_FIT`) / `komaT` (koma thickness = post thickness) / `standSlotSep(p) = height + 2*tabLen - komaT` (post spacing) / `maxRadius(p)` (post height = floor clearance).
  - **Implementation**: `komaR()` (koma side) being called by `standGeometry()` (stand side) is **the single cross-edge bridging koma ↔ stand**. The post height traces back through `standSaddleH() → maxRadius() → outerR()`, so it **depends on the profile core `outerR()`** ⇒ changing the profile automatically moves the stand dimensions too (the substance of the caveat below).
- `komaR`/`tabDepth`/`innerRi` are based on the smaller opening (`openMin`). Note that **changing the opening radius changes the koma size**.

## STL watertightness (mandatory verification)

The ribs, koma, and stand must be **watertight (closed manifold)** or the print slicer breaks. After touching geometry, verify by sweeping across a representative parameter range. The test is the "shared count of undirected edges":

- 2 = closed (normal) / 1 = open edge / >2 = non-manifold. Additionally, no NaN vertices and no degenerate (zero-area) triangles.

**Verification is `npm run check:manifold`** (`scripts/manifold.mjs`). It sweeps 3 presets × height/bamboo-rib diameter/pitch/board thickness/tolerance/plate count and inspects 41,472 parts, plus four narrower sections: Bézier handle editing, spiral winding, the **silhouette extremes** — the corners of `LIMITS`, which is the only section that scales the control points and therefore the only one that sees a steeply sloped face (see "How big may a design get") — and the **bottom ring's leg sockets**, the only section that runs `legSockets` off and the only one that tests a hole as a hole rather than as a closed shell (see "Leg sockets" above). Anything other than `0 FAIL` does not get merged. Additionally, for "refactors that shouldn't change the STL", use `npm run check:hash` (`scripts/hash.mjs`) to diff vertex hashes before and after the change and prove the shape didn't move (usage is in the comment at the top of the script). **`check:hash` is only comparable within one three.js version**: it hashes the position array in order, so a three upgrade that merely flips which diagonal splits a quad face rewrites every hash while the solid is untouched (this is exactly what r169 → r185 did to `boardGeometry`). Across a three upgrade, compare order-insensitive quantities instead — triangle count, signed volume, surface area, bounding box — which did stay identical for every part the sweep covered. The save feature's sanitize is verified by `npm run check:persist` (`scripts/persist.test.mjs`), confirming that corrupt localStorage (broken pts, numeric strings, oversized boards, unknown version, etc.) recovers safely without crashing or producing a non-watertight koma. Papercraft **and the washi template** are `npm run check:paper` (`scripts/paper.test.mjs`). The characters those PDFs print are `npm run check:glyphs` (`scripts/glyphs.test.mjs`): the writer draws anything outside WinAnsi from the outlines in `src/pdf-glyphs.js`, and a character with no outline is **dropped**, so a template that starts printing a new word prints a blank instead — on paper, where nothing else here is looking. It reruns `tools/pdffont`'s own collection over the same sources and fails both ways (a character with no outline; an outline nothing prints any more, which is the reworded-label drift `check:i18n` hunts in the dictionary). **`npm run lint`** is the one non-geometric gate: ESLint with **only** the two React hook rules (`rules-of-hooks` / `exhaustive-deps`, both errors — see `eslint.config.js` for why not `recommended`). A hook whose dependency array disagrees with its body is a stale closure — the viewport renders the design from three edits ago — and it is the one bug class here that is invisible in review *and* invisible to every geometric check. Opting out is fine, opting out silently is not: both existing exemptions carry an `eslint-disable` comment with its reason. UI wording is `npm run check:i18n` (`scripts/i18n.test.mjs`): because the dictionary is keyed by the Japanese string itself, **rewording a label does not make its translation stale — it deletes it**, and the app silently shows Japanese to an English visitor with nothing else in the build catching it. The script pins four shapes of that drift: a Japanese UI string with no EN entry (collected from every `t("…")` call, including calls nested inside template literals, plus every plain Japanese literal in `src/` — the latter also catches a label never wired through `t` at all), an **orphaned** EN entry whose key appears nowhere in `src/` (the fingerprint of exactly the reword above), a `{placeholder}` present on only one side (`t()` substitutes by name, so a dropped slot prints nothing and an invented one prints the braces), and a **duplicate key**, which JS resolves silently in favour of the last one — adding 「和紙」 for a guide card retranslated the inspector's own 「和紙」 heading, and 「竹ひご」 had been quietly overridden that way for some time.

Past failure causes and fixes: grooves too deep (→ cap depth at `higoD*1.5`), near-duplicate points on the barb's sharp flank (→ clean duplicate points before extruding), single-control-point presets (→ div-0 guard in `splineR` / denominators), a thin strip remaining in the lightening window at a waist (→ shrink/drop the window where it's thin), and **the lightening window cut straight through a groove on a steep face** (→ the band is slope-aware; see below).

**The lightening window's band is not a constant, and must not be turned back into one.** A groove is cut along the surface NORMAL (`grooveOuterPts`), so its tip does not land `depth` inside the smooth edge — it lands `depth × √(1+slope²)` inside, measured **in x at the tip's own height**, because the normal's y-component drags the tip up a face that is itself climbing in x. `lightenHoles2D` therefore takes `band(y) = max(bandW, grooveDepth(p) × √(1+slope²) + BAND_SOLID)`, worst slope over ±1.5mm so the 2mm chords between window samples cannot cut a corner either. `bandW` (11mm) stays the floor, so every design that was already clear of the notch keeps the exact window it had — 1144 of the 1152 parts `check:hash` covers are byte-identical; the 8 that moved are `barrel h140 higoD3`, whose surviving strip was **0.2mm**. `grooveDepth()` and `profileSlope()` live in `geometry/groove.js` and are shared with the cutter for the usual reason: the window and the notch have to be talking about the same groove.

**Two kinds of earcut degeneracy (you will always hit these as you increase the point count; handled by `cleanPoly()` and `Y_STAGGER`)**:
- **Collinear points**: sampling the curve finely lays hundreds of "points on the same straight line" along a flat span. The side walls are built exactly along the point list, but **earcut drops collinear points**, so the boundary between cap and side wall shifts and becomes an open edge. → `cleanPoly()` thins out collinear points in addition to duplicates. **Apply it to both the outline and the lightening window** (the window side originally had no cleaning, and that was the hole).
  - **Implementation**: the point-list → `THREE.Shape` conversion is **consolidated into the single function `shapeFromPts(pts, holes)`** (`src/geometry/shape.js`), which always applies `cleanPoly()` to both the outline and the holes. Build extrusion Shapes through here (writing it by hand forgets the cleaning and hits the degeneracy above — in fact `ribBandShape` had a copy of the cleaning that was missing only the collinear-point removal).
- **Same scanline**: if a lightening window's y-end lands at exactly the same height as an outline sample (`STEP=0.5mm`), the window corner and the outline vertex become collinear, producing a **zero-area triangle** and an open edge. → `Y_STAGGER=0.13` shifts the window's y-ends off the grid (`boardGeometry`'s `STAGGER=0.1` is the same fix).

## Papercraft (building from cardboard)

So it can be built without a 3D printer, the app outputs a **PDF** laying out each part's 2D outline at **A4 full scale (1:1)** (`src/papercraft.js` → `paperPDF(p, matT)`), downloaded from the print view **as `tomoshibi_katagami.zip`, with the washi PDF beside it** — one download per route, the same shape the STL kit's ZIP has (see "Washi template"). **The paper side has its own fixed items too**:

- **The template PDF is the mold only — ribs and koma.** The washi panel is the other file in the ZIP, never pages spliced into this one; see "Washi template" for why, and for the `paperP` the cardboard copy must be cut from.
- **It is a PDF, and it used to be a self-contained HTML page.** That page carried a screen-only preamble — print at "Actual size / 100%", no margins, fit-to-page off, a "save as HTML" button — every line of which existed *because* the medium was HTML. A PDF is already A4 at exact size, so the preamble went with it and the app says the one remaining thing (the printer's 100% setting) beside the download. Do not reintroduce an HTML route to get Japanese labels back; see the next point for the trade that was made knowingly.
- **The PDF follows the UI's language**, like the washi one — both are handed the app's own `t`. They were English-only until `pdf.js` carried its own outlines, because `winAnsi()` **drops** what it cannot draw rather than mangling it: a Japanese translator yielded parts labelled `" ×8"` with the word silently gone and every structural check still passing. `check:paper` section 5 pins both halves — every part name must appear in the English PDF's drawn text, and the Japanese one must **draw** an outline for every character WinAnsi cannot encode (counted against the same pages rendered as SVG; dropping them is the old failure, and it satisfies every other assertion).

- **The shape comes only from `geometry.js`'s pure functions.** Do not reimplement dimensions on the paper side (same rule as SectionEditor — if this drifts, the papercraft and STL produce different molds).
- **Don't cut the grooves (higo-me).** You can't carve a 0.5mm-precision V-notch into cardboard, so the outer edge is cut as a smooth curve (`ribOutline2D(p, k, { smooth: true })`) and the winding positions of the bamboo rib are shown with **dashed tick lines**. The positions come from the same `grooveList()` as the STL.
- **Don't open lightening windows.** Cardboard is light, and the windows only weaken it and add cutting work.
- **Material thickness `matT`** is the actual cardboard thickness the user measured. The koma's notch width is determined by it, so pass `{ ...p, boardT: matT, komaT: matT, fit: 0 }` **to all parts identically** (so the parts within the papercraft always mesh). Do not change the 3D side's `p`. `fit=0` (adding no print tolerance) is because cardboard's fibers crush as it goes in, so a nominal-exact fit meshes more firmly. For thick material it exceeds `maxBoards`, so **trim the rib count** and print a warning on the page.
- **Cardboard skips the tab-tip dent** (`noTabDent: true` in `paperParts`). The dent takes 6×6mm out of the tip's inner corner, which on cardboard is exactly where the tab is weakest — it tears along the flutes when pushed in. Cardboard trades the koma stop for tab strength and takes a **full-depth notch** instead; the koma is located by friction, which is enough because the fibers crush to a snug fit (`fit: 0`). `check:paper` asserts `tabDented(pk)` is **false** for every papercraft combination, so this cannot silently flip back.
- **The "koma wall is too thin" warning belongs to the APP, not the printed page.** The wall left between the koma's notches (`paperFit(p, matT)`) thins as the material thickens, and under half the material thickness it tears when hand-cut. Every way out of it — fewer ribs, thinner material, a wider opening — is a control in the app, so a warning on the printed page arrives after the sheet in your hand is already the wrong one. It is a **viewport alert** (bottom-right, alongside the bed-overflow one, which is the 3D-print route's counterpart; the two are mutually exclusive by route, and bottom-**left** is the section editor's legend). The rib-count clamp stays on the page as well, because that one also states what the template you are holding actually contains.
- **Don't output a stand.** The papercraft outputs **only the mold itself (ribs + koma)**; the user provides their own stand. (A "cross stand" made of two cardboard strips crossed in an X was previously generated, but it was confusing and was removed at the user's request. The 3D-print stand — `boardGeometry`/`standGeometry` — is unaffected; it's a separate part for the printed mold.)
- **The full-scale check mark is an L — a try square, not a bar — and it goes wherever the layout already leaves room.** Shrinking under the printer's "fit to page" is the biggest source of accidents, and this is the only way to notice it with a ruler after printing; one mark answers for the whole job, because a printer scales every page of it alike. It is drawn **thick** (the `scale` style, 0.6mm) so a ruler's edge has something to line up against.
  - **It has two arms because a printer can scale the two axes by different amounts, and a horizontal bar cannot see that at all.** This is why every printable sewing pattern prints a *square* rather than a line ([Seamwork](https://help.seamwork.com/hc/en-us/articles/360004182294-The-test-square-on-my-digital-pattern-is-too-small), [Sussex Seamstress](https://www.sussexseamstress.com/sewing-tips-blog/how-to-print-and-assemble-pdf-sewing-patterns)). Do not reduce it back to one line.
  - **It is an L rather than a full square because the two axes do not cost the same.** Width is free — 200mm of it mostly goes unused — while height comes straight out of the parts. So the long arm (3in) goes across and the short arm (3cm) goes down: enough to catch an axis that scaled differently, no more. Over the `check:paper` sweep a full 3in square costs **800 sheets against 712**.
  - **Both units ride the SAME arms**, a tick where the metric figure falls and another where the imperial one does (`5cm`/`3in` across, `1in`/`3cm` down) — not a mark each. Patterns normally print one square labelled "10cm (4in)", but **4in is 101.6mm**, so that label is wrong by 1.6mm and the reader cannot tell which unit the square is true to. Two ticks on one arm are exact in both. **Don't pair 5cm with 2in**: 2in is 50.8mm, near enough that someone checking the wrong mark with an inch rule reads "just under 2in" and believes a bad print is fine.
  - **`scaleSpot()` places it, not `pageOps`** — it is a mark, not a part, so it belongs in room the layout has *already* left, and most designs finish with half a sheet blank. Candidates are the band's top-left plus the bottom-right corners the parts leave (the standard corner heuristic); parts are tested by **bounding box**, deliberately conservative, because printing the one mark the sheet's scale is judged by across a cut line is worse than spending a page. Over the sweep it lands on sheet 1 for 232 designs and sheet 2 for 128, and the template prints **712 sheets**.
  - **`TOPBAR` (36mm) is the fallback, not the plan.** When nothing anywhere fits, sheet 1 gives up that strip and the square goes to its top-left. Keep both halves: reserving the strip unconditionally cost **736** sheets, and the version before that *only* looked for gaps and silently shipped **16% of designs with no check square at all**. Neither failure is visible in the app — you find out with scissors in your hand.
  - **Ticks run inward off their arm.** Outward ones can reach past `MARGIN`, outside the printable limit `MARGIN` is set to, and a tick the printer clips no longer says where the length ends.
  - **`TOPBAR` shifts the CONTENT down, never the frame.** The frame is the sheet's trim box and has to land in the same place on every sheet to be a reference at all; a top line 36mm lower on sheet 1 than everywhere else reads as a misprint. `ft = joinsPrev ? y0 : MARGIN` is what keeps those two apart.
  - This strip replaced a `FOOTER` band that took 14mm off *every* page. `FOOTER` is 0 now: the parts get the full height between the margins. Measured over the `check:paper` sweep, the template went from **761 sheets to 726** (27 designs a page better, none worse) once `MARGIN` came in to 5 as well, and to **712** once the check square stopped reserving a strip of its own.
  - **Nothing else is printed per sheet — no title, no page number.** The seam codes already say which sheet meets which, and a footer band costs content height on every page to repeat what the codes state where it matters. **A part is split across sheets only when it doesn't fit on one page.** Page layout is two stages: (1) pack parts into rows → (2) pack rows into pages, and **a row that fits on one page is never straddled** (if it doesn't fit, start the next page at the beginning of that row = nothing to join). Each page is clipped by `top`〜`bot`, where `bot` is "if the next page is a continuation of the same row, `top+CH`, otherwise the next page's start position". Without this distinction, the head of the next row prints onto the previous page's bottom edge and a seam appears where nothing is joined.

- **Sheets are joined by a blue frame plus coded half-diamonds — the convention home-print sewing patterns use** (`STYLE.frame` / `STYLE.join` / `STYLE.jlabel`, all `#1769c8`; blue on a pattern sheet reads as "align", never as "cut"). Three rules, and each one is load-bearing:
  - **The trim box is drawn identically on EVERY sheet**, seam or not — it is a fact about the paper, not about the parts on it. Each edge runs the whole width or height rather than closing into a box: lay two sheets up and the upper one covers the lower one's corners, which is exactly where a box keeps all of its information, and only a long line makes a small angular error visible.
  - **Sheets BUTT at the trim box; there is no glue tab, and there must never be a second line.** A glue tab necessarily puts the join line a centimetre inside the trim edge, so every sheet at a seam carries two blue lines a centimetre apart — one to cut on, one to align on — and no drawing makes that pair unambiguous. One line does both jobs: cut both sheets on it, butt the cut edges, tape from behind. This is the join the reference patterns describe ("trim any white printer border first, then the frames coincide"), and it hands each continuation sheet 10mm of content back. **A seam is therefore read from the row** (`next.row === row`), not from an overlap — there is no overlap left to detect. `check:paper` pins every horizontal frame line to `MARGIN` or the trim edge; a third value means a line is marking something that isn't there, which is how a bottom frame drawn at the end of the *content* band was caught.
  - **The half-diamonds are OPEN chevrons**, ends resting on the frame edge, apex pointing inward. Open because the frame line already draws their base; closing them lays a second stroke along the very line the sheets are aligned by and thickens it. Two sheets laid up correctly bring opposed chevrons base-to-base and the ◇ closes — a millimetre out and it visibly doesn't, which is why this beats "line the two lines up" (two lines on top of each other hide half a millimetre of error).
  - **Two per seam, a fifth in from each end, each with a code** (`1A`/`1B`, `2A`/`2B`, …). One mark leaves the sheet free to pivot on it, so two pin rotation as well as offset, and the angle they fix is only as good as their spacing. The codes remove all doubt about which edge meets which without printing a sentence across the drawing. The left/right chevrons carry **no** code on purpose: the layout is one column wide, so those edges have no neighbour to mate with and are trim marks only.
  - **There are no corner registration crosses, and the `reg` and `glue` styles are gone with them.** The box's own full-bleed intersections are the crosses, and better ones (they run to the paper's edge). Do not reintroduce both — that was the cluttered doubled-up corner this replaced. A style in the `STYLE` table that nothing draws is a lie about what is on the sheet, so delete the entry when you delete the last consumer.

Verification is `npm run check:paper` (`scripts/paper.test.mjs`). The test is not watertightness but **① being full scale (page dimensions = geometry.js invariants) ② no parts missing from the layout ③ no NaN in the SVG** (a renderer silently ignores NaN, so you'd only notice after printing). It reads the pages through `paperPagesSVG()` — the same `pageOps` the PDF is built from, rendered as markup, which is far easier to assert on than PDF bytes; the PDF's own structure is section 5. It additionally checks that **notch width = material thickness** and that **the tab-tip dent is never cut on cardboard** (both directly cause "won't fit when assembled" and can't be caught by looking at the paper), and that `paperFit()` — the cheap summary the app's alert quotes — agrees with the formula and with what `paperParts()` hands the template. Section 4 of the same script covers the washi template (see below): arc length / panel width against an independent integration of `outerR`, tick count = groove count, guides drawn as guides, and the panel appearing on its own sheets and **not** among the cardboard pages. Section 5 covers the washi **PDF**: every xref offset must land on its object header (a hand-rolled PDF that viewers refuse or open blank), page count = the SVG's, MediaBox = A4, the page CTM is mm→pt, the 50mm ruler really is 50mm, and no non-WinAnsi byte reaches a `Tj` string — Japanese leaves through the outlines instead, and the same section counts those: as many glyphs drawn in the Japanese PDF as there are non-WinAnsi characters on the pages rendered as SVG.

## Washi template (cutting the paper skin before pasting)

Trimming the washi **after** it is pasted is the fiddliest step of the build and a torn wet edge shows, so the app also prints the paper skin's own flat pattern: **one panel = the surface between two adjacent ribs**, at A4 full scale. `washiGore(p, {side, end, span})` in `geometry.js` → `washiParts` / `washiPDF` in `papercraft.js`. Fixed items:

- **The sheet's length is the meridian ARC LENGTH `∫√(1+R'²)dy`, not the body height.** (A 205mm body needs 217mm of paper.) Cutting to the straight height is exactly the failure this template exists to prevent — `check:paper` asserts the arc length against an independent integration of `outerR`, and the page states the number in text.
- **Half width = `π·R(y)·span/N`** = half the rib-to-rib arc. The run is **`fukuroRange` only** (the neck carries no washi), so the ends land on the opening radius = the sheet just covers the opening.
- **Flattening is inexact by nature** (the lamp body has Gaussian curvature ≠ 0). The straight-axis gore makes the side edge slightly longer than the true meridian — worst ~4% at the steepest slope with 8 ribs, ~2% with 12, shrinking as `(π/N)²`. **Do not "fix" this by scaling the width**: the width is what makes the panel meet its neighbours. The page reports the max slack instead (damp washi takes it up; more ribs reduce it). The exact alternative (a cone-chain unroll with a curved axis) buys accuracy with extra horizontal seams and is not wanted for a lantern.
- **Allowances are the only additions**: `side` (overlap, added on **each** side — panels lap over each other on the rib) and `end` (cover, past **each** opening — folded over the opening ring). Defaults 3mm/3mm, adjustable in the UI, persisted like `matT`. The end overhang keeps the opening's width, which is exact because the neck is a vertical rectangle.
- **Guides are never cut lines.** The dashed guides mark the true rib lines (inset by `side`) and the opening lines; the short ticks mark the bamboo positions from the same `grooveList()` as the mold. They are traced from the same station list as the cut outline, so they can't drift off a sharp shoulder.
- **The template is traced, not glued on** — washi is translucent, so it is slipped under the paper. Never instruct the user to glue it to the material (that is the cardboard template's flow, not this one).
- **There is no on-screen preview of the washi panel, and it is not an oversight.** It is one sheet of one shape; it says nothing about the mold on screen, and the PDF is opened in a viewer that shows it better than a 190px dock did. A dock existed briefly on both routes (`WashiPreview` + `.pages-dock`) and was removed at the user's request — do not rebuild it, and do not draw the panel a second way for a thumbnail either. What the app says about the washi on screen is the 「和紙」 section's numbers.
  - **`washiPagesSVG()` survives that removal on purpose**: it is the SVG encoding of the very pages `washiPDF` writes, and **`check:paper` section 6 compares the two coordinate by coordinate** — every path and every label of both deliverables (3,942 paths over 36 designs), plus the fact that the UI language moves no coordinate. Section 5 pins the page counts. That comparison is what stands between a hand-rolled PDF and a file that disagrees with everything else here, and markup is the encoding you can assert on. The three encoding differences section 6 tolerates are named in its comment (2dp vs 3dp rounding, `text-anchor: middle` vs a pre-shifted x, `&lt;`); a fourth appearing means a renderer has drifted, not that the tolerance needs widening.
- **The washi template is not an output method, and has no download of its own.** It is not another way to make the mold — it is the paper skin you need on top of whichever mold you built, so it lives with the design settings (the 「和紙」 section: overlap / cover / panel size) and **rides along with whichever output you pick**, as `tomoshibi_washi_a4_beta.pdf` inside that route's ZIP: beside the STLs on the 3D route, beside `tomoshibi_katagami_a4.pdf` on the cardboard one. Do not re-add it to the output toggle: the toggle is mutually exclusive, and the washi is needed in both cases. One download per route, one deliverable per document — that is the shape, and a second CTA for the washi breaks the first half of it.
  - **It is its own PDF on the cardboard route too, not pages appended to the mold's template** (`paperParts` used to append them; it does not any more). The two are printed at different moments — the mold once, the skin once per lantern, often on different paper — and `pagesPDF` numbers and seams the sheets of *one* document, so splicing two deliverables together makes the seam codes span things that never join.
  - **Its panel width follows the rib count, so the cardboard copy is cut from `paperP(p, matT)`** — the *clamped* `pk.boards` = the mold that template actually makes. That is why `paperP` is exported: the studio hands the same `washiSrc` to `washiPDF` and to the dock, so the sheets on screen and the file in the ZIP are cut for the same mold. `check:paper` section 1 pins it (a clamped count must widen the panel), section 4 pins the split (the panel is on its own sheets and **not** on the cardboard pages), and section 5 pins it in the shipped bytes.
- **The washi template is marked `beta` — in the panel AND in the filename** (`WASHI_PDF` in `TomoshibiStudio`, one constant for both ZIPs and both notes). Flattening a doubly-curved surface is approximate by nature (see above) and how much a damp sheet takes up has not been checked against enough real builds. The dimensions are verified; the fit on a real lantern is not, and the panel readout is not a promise. The badge in the 「和紙」 section's hint is the same one, for the same reason, as the cardboard route's — but the **filename** is the half that matters, because the file outlives the screen it came from: it gets mailed, reprinted months later, handed to someone who never saw the app.
- **The PDF is labelled in whatever language the app is showing.** It carries no CJK font — embedding one would dwarf the file — but it does carry outlines for the characters it prints (see `pdf.js` / `tools/pdffont`), so Japanese draws and only an unlisted symbol still folds through `winAnsi()`. Nothing dimensional depends on the labels — but keep the ruler note short in **both** languages (a long line collides with the right-aligned footer, which no CSS will save you from in a PDF).
- **Pages are built once as drawing ops** (`pageOps`) and rendered as SVG *or* PDF. Add a new page element there, not in one renderer — and the line/text styles live in the `STYLE` table (the stylesheet is generated from it) so the renderers cannot drift. The **in-app preview is not a third renderer**: `paperPagesSVG()` hands it the same `pageSVG()` markup the printable HTML is built from. It only asks for the CSS scoped (`styleCSS(".pages ")`), because those class names — `.note` among them — are the inspector's too.
- **All panels are identical, spiral winding included** (every bay sees the same helix), so one sheet is laid out labelled `×N`. Spiral only shifts the right-edge ticks by `step/boards` — that is `grooveList(p, gR, 0)` vs `grooveList(p, gR, 1)`, not a separate calculation.

## Build route (3D print vs cardboard)

Which route someone is on — `route`: `"stl"` / `"paper"` — is **app-level state held in `TomoshibiStudio` and persisted** (`persist.js`, alongside the bed dimensions; anything but `"paper"` sanitizes to `"stl"`). It is not a per-export toggle: it is a fact about the maker, and the rest of the app branches on it.

- **The print bed only exists on the STL route.** Cardboard prints on A4 and anything larger simply **continues onto the next page, butt-joined** — so there is no size limit to warn about. `bedRules = route === "stl"` gates the overflow warning (in *every* view, not just the print view — it used to nag a cardboard user in the section view), the "→ lower the body height to Nmm" hint, and the warn colouring on the rib-length readout. Do not reintroduce a bed check that ignores the route: shrinking a design for a limit that route doesn't have is the bug this prevents.
- **The print view is a different kind of view per route.** STL gets the 3D plates (`buildPrint`); cardboard gets **`src/PagePreview.jsx`** — the template's own A4 pages as SVG over the (idle) canvas, exactly the way the section editor overlays its SVG; `buildScene` returns early for it, the same as for `"2d"`. **Its output is a document, so its preview is a document** — there is nothing spatial to show, and a WebGL page needs a canvas texture to say what a stroke of ink says for free. **Neither view previews the washi template** — it downloads as a PDF and is read as one (see "Washi template").
- **The preview never lays parts out itself.** It renders `paperPagesSVG()` — the same ops, through the same renderer, as the printable HTML — so the page count, the parts on each page and the part spanning two pages are the template's own answers. An earlier version packed the parts onto a field of A4 sheets of its own devising; the moment that disagrees with the template, the user believes the wrong one. On screen it is **not** full scale (hence the note, and hence the printed ruler).
- **The guide branches on the route too, and reads it through `paperP`.** On cardboard the page describes the mold that route *makes*: the material thickness becomes the board thickness, thick material clamps the rib count, the ribs are drawn with a **smooth outer edge and no lightening windows** (the template cuts neither), and the stand and ring steps are filtered out rather than reworded. Building it from the design on screen instead is the same bug the washi panel had — a page that counts ribs the template does not cut.
- **The choice is offered on the welcome card**, and switched in the print view by the segmented chip **on the viewport, next to the mode tabs** — not in the inspector. It changes what the whole view *is*, so it does not belong at the bottom of a long scroll; the panel below it only holds that route's settings (bed size / material thickness) and names the route in its section hint.

## Onboarding (first-time visitors)

The app is published on a static host, so most first-time visitors arrive knowing nothing — and in English (`loadLang()` defaults to `en`). Two pieces cover them, deliberately split by the question they answer:

- **"What is this?" → `src/Welcome.jsx`**, one card shown on the first visit. The object on screen is not the lantern, it is the *mold*; the output is an STL or a full-scale paper template; the washi template comes with either one. **One card, not a step-through tour**: the app is a single screen with no empty state, and a spotlight overlay would have to track a viewport that stretches (the section view is a `preserveAspectRatio` SVG). Esc / backdrop / button all close it, and it never blocks anything.
- **"3D printer or cardboard?" → the two buttons on that same card.** The route decides whether the bed constrains the design at all, and the bed's warning starts nagging long before anyone opens the print view — so it is asked once, up front, rather than left to a toggle buried at the bottom of the panel. **Each button is also the start action** (pick → the card closes), and 「とりあえず見る」 leaves the saved route alone. The card is presentational still: it takes `route` + `onPick`, and owns neither.
- **"How do I work the ◇?" → the legend at the bottom-left of `SectionEditor`.** It **redraws the canvas marks themselves** (control point, selection ring, add-point ghost, height handle, tangent handle) at legend size in the same shapes and colors, rather than describing them in words. Its content follows `editMode`: in curve-adjust mode the `+` ghosts are hidden and the point itself doesn't move, which reads as a bug unless the legend says so.

Fixed points:

- **The dismissal flag is `tomoshibi.welcome` (`persist.js`), separate from the design state.** Exporting/importing a design must not carry "has this person seen the intro", and clearing one must not touch the other.
- **Auto-open keys on that flag ALONE — do not add "…and there is no saved design".** The autosave flushes on `pagehide`, so a first-time visitor who merely reloads before touching anything already has saved state and would never see the card, which is exactly the person it is for. The cost is that an existing user meets it once.
- **The cardboard button keeps its `beta` badge here.** This card is where someone chooses that route, and offering it without the caveat would sell a route that has had far less real-world building behind it.
- **The "?" in the inspector header is the only way back.** Once dismissed the card never auto-opens again, so don't remove that button (note the inspector is hidden in lit mode — that's fine, lit is a viewing mode).

## Conventions

- **Comments are in English** (match the existing style). Write units and intent for formulas and dimensions.
- **UI strings are Japanese, and the Japanese IS the dictionary key** (`i18n.js`). So **editing any user-facing wording means editing `EN` in the same commit** — the old key does not warn, it just stops matching. Run `npm run check:i18n`; it fails on both halves of that mistake (the new wording with no translation, and the old entry left stranded).
- Keep `geometry.js` as **pure functions** (don't bring in React/DOM). Otherwise the section view and STL will drift.
- So the shape matches across views, always draw the section view (SectionEditor) using `geometry.js`'s functions (**including the dimensional constants** — don't reimplement them yourself). The groove half-width is consolidated into `grooveR(p)` (this used to be split between `higoD/2+0.15` and `+0.25`, and the section view drew a thinner groove than the STL).
